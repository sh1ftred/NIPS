# MSB Ruleset 334001: SEC Rovers
##### NIP1962 STATUS:RAW; Version: 00; Hex code `334001`

A **Rover** is a Sovereign Economic Community (see [MSBR334000](MSBR334000.md)) that is *part of* a larger SEC. The larger SEC is the rover's **carrier**.

A rover is a rocket in full: it has its own `d`, its own `ignition` event, its own state, its own mission, its own problem statement, its own merits, its own votepower and its own tip. The only thing this ruleset adds is the *declared link upward*, so that clients can present a forest of SECs instead of a flat list of unrelated ones.

A rover is not a sub-state, a category, or a tag on its carrier. It is a separate Microsubjective Blockchain that says which SEC it is part of. This keeps the relationship **permissionless**: a rover can be ignited by anyone at any time, and its carrier does not have to know, agree, or change its state.

This ruleset **composes with** MSBR334000 and does not replace it. A state event that declares `334001` MUST also declare `334000`.

```
["ruleset", "334000"]
["ruleset", "334001"]
```

### Ruleset Updates
As MSBR334000: this ruleset requires `>80%` of the SEC's `votepower` to add or remove ruleset identifiers and `>60%` to increment a ruleset identifier to the next stable version.

### The Carrier Link
A rover declares its carrier with the standard addressable pointer tag, carrying the marker `carrier`:

`[ "a", "31108:<carrier pubkey>:<carrier d tag>", "<relay hint>", "carrier" ]`

| RFC 2119 | Description | Spec or Example |
|---|---|---|
| MUST | The carrier's addressable coordinate. Event IDs are not permitted. | `["a", "31108:4bf150c3…:Routstr", "wss://relay.routstr.com", "carrier"]` |
| MUST | The marker `carrier` in the fourth element | see above |
| SHOULD | Included by the creator in the rover's `ignition` event, like the problem statement and image in MSBR334000 | see above |
| MAY | Repeated, when one rover is part of more than one carrier | one tag per carrier |

A carrier link MUST be a **coordinate**, never an event ID. Event IDs rot: in the September 2026 corpus of `kind 31971` events, parent *coordinates* were retrievable 36/36 times while parent *event IDs* were retrievable only 5/34 times (see [Problems.md](Problems.md), *Event references rot; coordinates do not*). The same reasoning applies here.

The `carrier` marker MUST be present. An `a` tag on a `kind 31108` event that points at a `31108` coordinate but carries no `carrier` marker is a *mention*, not a carrier edge, and clients MUST NOT nest on it. On other event kinds an `a` tag naming a `31108` coordinate already means "the SEC this event belongs to" (see [Products.md](Products.md), [Merits.md](Merits.md)); this section constrains `kind 31108` only.

### A carrier MUST NOT be required to list its rovers
Rovers point up; carriers do not point down. Enumerating rovers inside a carrier's state would make every new rover a change to the carrier, and under MSBR334000 that means a `>80%` votepower vote before a new rover can exist. Requiring permission to be part of a bigger SEC is exactly the failure mode this ruleset is written to avoid.

Consequently a carrier's state event SHOULD NOT contain a list of its rovers, and a client MUST NOT treat the absence of such a list as evidence that no rovers exist.

### Identity
* A rover's `d` MUST be unique among the SECs published by the same pubkey. This is not cosmetic: `kind 31108` is addressable by `(pubkey, d)`, so a rover published from the same key as its carrier, with the same `d`, **is** the carrier — the newer event replaces the carrier's state and the carrier is lost. A rover SHOULD use a name distinct from its carrier's.
* Publishing rovers from their own key is RECOMMENDED, because it makes the collision above impossible.
* A rover keeps its own coordinate for life. A revision keeps the same `pubkey` and `d` and MUST follow NIP-31108: it names the `ignition` event and the ID of the previous `31108` from the **same pubkey** in its `parent` tag.
* The `d` tag is free-form. MSBR334000 does not constrain its length or character set, and this ruleset does not add a constraint.

### Discovery
To build the forest of SECs, a client:

1. fetches `kind 31108` events and keeps the newest `created_at` per addressable coordinate — count **coordinates, not events**, because a relay may serve a superseded revision alongside the head;
2. reads the `carrier` marker tag on each head, if present;
3. treats SECs without a carrier tag as roots, and nests each rover under its carrier coordinate.

A rover whose carrier coordinate is missing from the discovered set MUST still be displayed, marked as **detached**, together with any of its own rovers. A carrier that has been deleted, pruned, or published to relays the client cannot reach MUST NOT make its rovers disappear.

Carrier links MAY form a graph rather than a tree, because the tag may repeat and two SECs may name each other. Clients MUST break cycles rather than recurse forever, and SHOULD surface the members of a cycle as detached roots so that nothing is hidden.

### Votepower, Merits and Sats
* Merits held in a rover confer **no** votepower in its carrier, and merits held in a carrier confer no votepower in its rover. A rover is a separate SEC that is part of a larger one, not a subsidiary of it.
* A carrier MUST NOT modify a rover's state. Changes to a rover's state require `>80%` of the rover's own votepower, exactly as for any other SEC.
* A rover MAY set `["crossfunding", "true"]` (MSBR334000) so that Approved Merit Request holders from other SECs can acquire its own AMRs. Note the limitation: that gate is not carrier-specific. It opens the rover's AMR market to holders approved in *any* SEC, not only in the rover's carrier.
* This ruleset defines **no** revenue share, no payment routing, and no sats flow between a carrier and its rovers. An SEC that wants the carrier to receive a proportion of a rover's revenue, or the rover to distribute to the carrier's holders, MUST define that in a further ruleset.

### Problem Statements
MSBR334000 puts an SEC's problem statement on its state event. A rover's problem statement SHOULD be a problem in its **carrier's problem tree** — conventionally a child or deeper descendant of the carrier's own problem statement, per [Problems.md](Problems.md).

This is what makes the composition legible on both layers at once: the carrier's tree shows what is unsolved and how it decomposes, and each rover's state shows who has taken a piece of it and what they are selling. A rover whose problem is not in its carrier's tree is still valid, but clients SHOULD render the link as narrative rather than as scope.

### Client Behaviour
| RFC 2119 | A client |
|---|---|
| MUST | nest a rover under its carrier when the `carrier` marker tag is present |
| MUST | display a rover whose carrier coordinate is unresolvable, marked detached |
| MUST | break carrier cycles instead of recursing forever |
| MUST NOT | treat an unmarked `a` tag pointing at a `31108` coordinate as a carrier edge |
| MUST NOT | require a carrier to enumerate its rovers |
| SHOULD | group `kind 31108` events by coordinate before reading carrier tags |
| SHOULD | show a rover's problem statement, mission and image as it would for any SEC |
| MAY | label a rover whose carrier has not itself declared `334001`, but MUST still display the nest |

>#### Case Study: Routstr
>**Carrier:** `31108:4bf150c3df7c821233a3525e2039cebaafa63504f4644304fc507a2cf0f121dd:Routstr`
>**Mission:** _Open, permissionless AI inference, ranked by your community._
>
>A rover could be ignited for one branch of the Routstr problem tree, for example:
>
>```
>31108:<rover pubkey>:Routstr-Lightning
>  ["ruleset", "334000"]
>  ["ruleset", "334001"]
>  ["ignition", "this"]
>  ["parent", "this"]
>  ["mission", "Direct Lightning payments for Routstr buyers, without a mint in between"]
>  ["a", "31108:4bf150c3df7c821233a3525e2039cebaafa63504f4644304fc507a2cf0f121dd:Routstr", "wss://relay.routstr.com", "carrier"]
>  ["problem", "31971:4bf150c3df7c821233a3525e2039cebaafa63504f4644304fc507a2cf0f121dd:dcd80ee81902861eddb52552c4566a29405dde3702775d709565fa9d930510cd", "wss://relay.routstr.com"]
>```
>
>_Direct Lightning_ is already a problem in the Routstr tree, a great-grandchild under *Payments and audits*. The Rover declares, in one event, that it is part of Routstr, what specifically it is for, and what it has to sell — without Routstr's state changing, and without anyone's permission.

### Non-normative: why the link is not `parent`
NIP-31108 already assigns `parent` on a `kind 31108` event:

> Pointer to the ID of the last `kind 31108` that this replacement is updating (MUST be the same pubkey), or `"this"` if it itself is the ignition event.

That is the MSB chain pointer, and it is what lets anyone walk the state history back to the `ignition` event. Putting a carrier coordinate there does not just overload a name, it breaks two things at once: a client that follows `parent` can no longer find the previous state, and a client that follows carrier coordinates can no longer tell a hierarchy from a chain.

The failure is already visible in practice. The Routstr rocket has been revised twice, so its live head carries `parent = d1fa2932bd88ac654c3d95fbf9316110689383c081ccd89ab0dbe455c4521c83` — a previous state event ID, as the spec requires. A client that reads `parent` as a carrier coordinate cannot resolve it, and reports Routstr as a rocket with a *detached parent* rather than as a root. Any SEC that has ever published a replacement looks broken under that reading, and a rover that put its carrier in `parent` could never publish a valid replacement at all.

Two further spellings were considered and rejected:

* **v1 used `["e", <parent ignition event ID>, "parent"]`** (see [legacy/Rockets.md](legacy/Rockets.md)), with membership gated on the parent's Identity Tree. It is rejected here because it uses an event ID, because `parent` is now taken by NIP-31108, and because gated membership makes being part of a larger SEC a matter of permission. Rovers are open; an SEC that wants a gated member set MUST define that separately.
* **A new multi-character tag name** (for example `sec` or `super`) is rejected because multi-character tag names are not indexed by khatru-based relays and therefore cannot be queried; `#a` is not only indexed, it is already the spelling this specification family uses for "the SEC this event belongs to".
